# Инвентаризация UI калькулятора толщин такелажа

Этап 0 доработки страницы [/tools/rigging-diameters](https://www.glushkov-modelling.com/tools/rigging-diameters).
Документ фиксирует факты до изменений интерфейса, источники данных для
группировки и контроля и принятые решения слоя отображения.

Дата: 2026-11-16. Ветка: `feat/rigging-ui-hierarchy`.
Основание: задача «Доработки UI калькулятора такелажа» и ТЗ v1.0.

## 1. Что есть сейчас

- `src/pages/tools/rigging-diameters.astro` — SSR-страница формы, профилей и
  контейнера результатов; стили страницы локальные, на токенах сайта.
- `src/scripts/riggingCalculator.ts` — клиентский контроллер: читает форму,
  отправляет конфигурацию в Worker, рисует ведомость.
- `src/lib/rigging/*` — чистое расчётное ядро и словари подписей. Страница
  использует те же документы профилей, что Worker.
- API: `POST /api/rigging/v1/calculate` (`rigging-calculator-worker`).
- Текущая ведомость — плоский список секций по `ownerId`; фильтр — одна
  группа кнопок `Standing / Running / Bowsprit / Anchor / Guns`, где узлы и
  виды такелажа перепутаны. Именно поэтому бушпритные снасти исчезают при
  выборе `Standing`, хотя ватер-штаг — стоячий такелаж.
- Подробности строки (`<details>`) содержат формулу, базу, коэффициент,
  материал, точку измерения, источники, предупреждения и кнопку подбора нити.
- Подбор нити открывается модалкой и ничего не запоминает: в строке нет
  колонки Thread и состояния выбранной нити.

## 2. Источники данных для представления

Поля `RiggingResult` — единственный вход слоя отображения; повторный расчёт
для группировки, поиска и фильтрации не нужен.

| Что нужно | Источник | Проверка |
| --- | --- | --- |
| Узел | `ownerType` + `ownerId` | `fore`, `main`, `mizzen`, `bowsprit`, `anchor_group`, `gun_group`, `hull` |
| Ярус | `tier` | только у `ownerType = mast`; `lower` / `topmast` / `topgallant` |
| Вид такелажа | `group` | `standing` / `running` у мачт; `bowsprit` / `anchor` / `gun` — самостоятельные категории |
| Статус | `status`, `reasonCode` | `calculated`, `needs_input`, `unsupported`, `not_applicable` |
| Материал | `material` | отображение сохраняется как есть, фильтров по материалу нет |
| Вариант правила | `variant`, `alternativeGroupId` | `compound` / `simple` у рейных снастей |
| Порядок в профиле | `sortIndex` | задаёт порядок строк внутри листа по умолчанию |
| Ключ строки | `ownerId`, `nodeId`, `ruleId`, `tier`, `variant` | см. `src/lib/rigging/ledgerKey.ts` |

Проверка метаданных правил всех профилей: ключи правила — `ruleId`, `role`,
`name`, `group`, `select`, `base`, `factor`, `materials`, `material`,
`coefficientBasis`, `calibrationStatus`, `requires`, `unsupportedWhen`,
`variant`, `alternativeGroupId`, `perMastOverrides`, `sources`, `warnings`.
Отдельного поля `riggingType` нет. У правил `group = bowsprit` нет
подтверждённой классификации standing/running, поэтому она не выводится из
названия снасти и не добавляется в ядро.

## 3. Контрольная ведомость

Полная конфигурация `traditional_plant 1.1.0` (все блоки, которые показывает
профиль), масштаб 1:64:

- 279 строк, 135 правил, 23 конечных группы «узел + ярус + вид».
- По узлам: фок-мачта 84, грот-мачта 72, бизань-мачта 78, бушприт 25,
  якорная группа 16, орудия 4.
- По видам: running 153, standing 81, bowsprit 25, anchor 16, gun 4.
- По статусам: calculated 270, unsupported 9 (`rule_not_supported`:
  topmast tack, topgallant tack и topgallant reef fall на каждой мачте).
  `needs_input` и `not_applicable` в полной конфигурации не возникают — их
  нужно проверять отдельными конфигурациями и синтетическими строками.
- 63 строки без яруса: фок-мачта 12 (косые паруса), бизань-мачта 6 (гафель),
  бушприт 25, якоря 16, пушки 4. У грот-мачты строк без яруса нет.
- 9 строк без диаметра — ровно те же 9 `unsupported`. Нулевой диаметр не
  подставляется.
- 27 строк с `variant` и `alternativeGroupId` (рейный hoist: compound/simple).
- 174 повторяющихся английских названия: одно правило повторяется по мачтам.
  Название не может быть идентификатором; контекст узла и яруса обязателен.

Другие профили в полной конфигурации:

| Профиль | Версия | Строк | Без яруса | Узлы |
| --- | --- | --- | --- | --- |
| traditional_plant | 1.1.0 | 279 | 63 | мачты, бушприт, якоря, пушки |
| early_plant | 1.2.2 | 106 | 19 | мачты, бушприт, якоря, hull |
| yacht_metal_schooner | 1.1.0 | 99 | 72 | мачты, бушприт |
| yacht_metal_yacht | 1.0.0 | 15 | 6 | только мачты |

Следствия для UI: секции строятся по фактическим данным, а не по словарю;
«Hull & general rigging» появляется только там, где есть строки `hull`;
искусственные мачты, ярусы и узлы не создаются.

## 4. Ключ строки

`ledgerRowKey` = `ownerId|nodeId|ruleId|tier|variant` (пустой `tier` или
`variant` — пустая часть). Ключ не включает индекс отображения, название,
диаметр, статус и материал.

- Уникален на 279/279 строках контрольной ведомости и на полных
  конфигурациях всех четырёх профилей.
- Различает compound/simple и ярусы одной снасти.
- Переживает фильтрацию, сортировку, смену режима и повторный расчёт, пока
  строка остаётся той же снастью в том же узле и ярусе.
- Инварианты зафиксированы в `tests/rigging-control.test.ts`.

## 5. Пробелы и ограничения, принятые до разработки

1. **Бушприт без вида такелажа.** `group = bowsprit` — категория узла, а не
   вид. При фильтре `Standing`/`Running` бушпритные строки не участвуют; `All`
   их сохраняет. Это объясняется подсказкой фильтра. Ядро не меняется.
2. **Нет состояния выбранной нити.** Модалка подбора только показывает
   варианты. Этап 1 добавляет колонку Thread и безопасную передачу выбора из
   модалки; этап 3 — сохранение, повторное применение и экспорт.
3. **Нет DOM-тестового окружения.** Логика представления выносится в чистые
   модули и проверяется `node --test`; визуальная проверка — системный Chrome
   в headless-режиме на 360/390/768/1280 CSS px, без новых зависимостей.
4. **Строки без яруса.** Не относятся к нижнему ярусу и не растворяются в нём:
   для них предусмотрен явный раздел «No tier» внутри секции мачты.
5. **Дубли названий.** Поиск и сортировка работают по названию, но контекст
   узла и яруса всегда показывается в строке и результатах поиска.

## 6. Решения слоя отображения для этапа 1

- Порядок секций: фок-, грот-, бизань-мачта, бушприт, hull, якоря, пушки;
  незнакомые `ownerId` — после известных, без потери строк.
- Внутри мачты: `Lower mast`, `Topmast`, `Topgallant`, затем `No tier`.
- Внутри яруса: `Standing rigging`, затем `Running rigging`. Если вид один —
  заголовок вида не дублирует секцию. У бушприта, якорной группы и орудий
  уровня вида нет: строки идут прямо в секции.
- Секции узлов раскрываемые (`<details open>` при первом расчёте); ярусы и
  виды — заголовки, без обязательного клика на каждом уровне.
- Фильтры `Node`, `Tier`, `Rigging type`, `Status` независимы, одиночный
  выбор + `All`, между собой и поиском — AND. Опции строятся из полной
  ведомости текущего расчёта, не из уже отфильтрованной выборки.
- `M` — строки текущего расчёта с учётом `Show not applicable`; `N` — после
  поиска и фильтров. `M` и `N` используют те же правила состава, что экспорт.
- Поиск: RU и EN одновременно, по части слова, без учёта регистра и е/ё,
  несколько слов — все должны найтись в одном из названий строки.
- Сортировка по названию и диаметру: в grouped-режиме внутри конечной группы,
  в flat — по всей выборке. Строки без диаметра всегда последние.
- Переключение режима и сброс фильтров не меняют расчёт, подбор нити и
  выбранную конфигурацию.

## 7. Контроль и базовая линия

- `tests/fixtures/rigging-control.json` — снимок 279 строк: ключи, группы,
  ярусы, варианты, статусы, материалы, базисы, диаметры и SHA-256.
- `tests/rigging-control.test.ts` — сравнение снимка, уникальность ключей и
  структурные инварианты для всех профилей.
- Снимок обновляется только вместе с отдельно согласованным изменением
  расчётного ядра; интерфейсные этапы его не трогают.
- Базовая линия до этапа 0: `npm test` — 134 теста, `npx astro check` — 0
  ошибок и предупреждений, `npm run build` — успешно; API расчёта отвечает 200.
