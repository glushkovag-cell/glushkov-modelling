# Калькулятор канатов — спецификация

Статус: контракт калькулятора. Реализация — Worker, Web Component и MCP-адаптер.

| Контракт | Пути | apiVersion | algorithmVersion | Статус |
| --- | --- | --- | --- | --- |
| v2, текущий | `/api/rope/v2/*` | `2` | `4.0.0` | актуальный, без груза |
| v1, заморожен | `/api/rope/v1/*` | `1` | `2.0.0` | совместимость, числа не меняются |

`modelId` актуальной модели — `log-dtex-quadratic-no-load`. У v1 отдельного
`modelId` нет: это замороженная степенная формула.

## 1. Назначение

Калькулятор оценивает диаметр трёхпрядного каната по линейной плотности нити и
числу нитей в пряди, а также подбирает нити каталога под целевой диаметр.
Расчёт и каталог живут только в Cloudflare Worker. Frontend и MCP-сервер
обращаются к JSON API и не дублируют ни формулу, ни данные.

Модель не использует нагрузку: ни в расчёте, ни в запросах, ни в ответах нет
поля груза. Контракт v2 с учётом груза (algorithmVersion 3.0.0) снят с
эксплуатации; его материалы сохранены в `docs/rope-calculator/archive/load-v2/`.

## 3. Модель

`x` — dTex покупной исходной нити, `n` — число нитей в одной пряди, `D` —
диаметр в миллиметрах. Прядей всегда три. `u = ln(x / 300)`, `v = ln(n)`,
натуральный логарифм.

```txt
D = exp(-0.8841755979848913
      + 0.6318544934210768 × ln(x / 300)
      + 0.5435747556354212 × ln(n)
      - 0.061470048768181726 × ln(x / 300)²)
```

- Модель лог-квадратична по `x` и лог-линейна по `n`; четыре коэффициента.
- Груз, бренд, материал и источник в формулу не входят.
- Расчёт выполняется в `float64` без промежуточного округления. Округление
  допустимо только при отображении.
- Константа 300 в нормировке — часть модели, а не параметр и не «типичный
  груз»: она задаёт точку разложения и не заменяет нагрузку.
- Коэффициенты и версия алгоритма хранятся в коде Worker, а не в ACF: правка
  коэффициентов — изменение поведения, а не контента.

История версий алгоритма:

- `4.0.0` — модель без груза (текущая), контракт v2.
- `3.0.0` — модель с учётом груза, контракт v2 (снята с эксплуатации).
- `2.0.0` — `D = 0.0204055952 × dtex^0.5293147610 × n^0.5366123919`, контракт
  v1, заморожен.
- `1.0.0` — `D = 0.01752 × dtex^0.5437 × n^0.5880`, `n` = 1–3.

Запрещены дополнительные поправки по бренду, источнику или нагрузке без нового
исследования и отдельной версии алгоритма.

## 4. Валидация входов

### 4.1. Актуальный контракт v2

| Поле | Правило |
| --- | --- |
| `basis` | `catalog` или `dtex`; для `catalog` обязателен `threadId`, для `dtex` — `dtex` |
| `dtex` (ручной ввод) | конечное число от 22.22 до 6000 включительно |
| `dtex` (каталожный) | принимается как есть; диапазон 22.22–6000 к нему не применяется |
| `threadsPerStrand` | целое от 1 до 5 включительно |
| `threadId` | непустая строка, существует в каталоге и `enabled` |
| `targetDiameterMm` | конечное число больше нуля |
| `threadIds` | массив непустых строк; поле отсутствует — проверяются все активные нити; пустой массив — ошибка 422 |

Некорректные типы, `NaN`, `Infinity`, ноль и отрицательные значения — ошибка
параметров, а не скрытое приведение или `clamp`.

Нижняя граница 22.22 нужна для новых измеренных тонких нитей и одинаково
действует в Worker, интерфейсе и MCP. Верхняя 6000 совпадает с самым толстым
каталожным значением; для каталожных нитей проверка диапазона не применяется,
иначе две существующие нити стали бы нерабочими.

В поле интерфейса допускается десятичная запятая: она нормализуется до точки
на границе UI. HTTP и MCP принимают только JSON numbers.

### 4.2. Устаревшие поля нагрузки

Поля `loadMode`, `loadGrams`, `load`, `appliedLoadGrams`, `recommendedLoadGrams`,
`recommendedLoad`, `loadRecommendationVersion` были опубликованы в контракте
v2 с учётом груза. Теперь они не поддерживаются: запрос с любым из них
отклоняется с `422 INVALID_PARAMS`, в `fields` перечислены все неподдержанные
поля. Молча игнорировать их запрещено — клиент получил бы результат, не
соответствующий запросу. Legacy-endpoint с грузом не вводится.

### 4.3. Замороженный контракт v1

Правила прежние: ручной `dtex` 80–6000, `n` 1–5, `threadIds` и
`targetDiameterMm` как в v2, каталожные значения без проверки диапазона.
Формула v1 не меняется. Поля нагрузки в v1 тоже отклоняются как
неподдержанные, чтобы неработающий параметр не был принят молча.

## 5. Прямой расчёт

`POST /api/rope/v2/forward`

```json
{ "basis": "catalog", "threadId": "tera-40", "threadsPerStrand": 2 }
```

```json
{ "basis": "dtex", "dtex": 750, "threadsPerStrand": 2 }
```

```json
{
  "apiVersion": "2",
  "algorithmVersion": "4.0.0",
  "modelId": "log-dtex-quadratic-no-load",
  "catalogVersion": "0b24290aff0e",
  "fetchedAt": "2026-11-17T13:00:00.000Z",
  "warnings": [],
  "basis": "catalog",
  "input": { "threadId": "tera-40", "dtex": 750, "threadsPerStrand": 2 },
  "result": {
    "basis": "catalog",
    "threadId": "tera-40",
    "dtex": 750,
    "threadsPerStrand": 2,
    "strands": 3,
    "construction": "2 × 3",
    "diameterMm": 1.0201549921706878
  }
}
```

Для `basis: "dtex"` поля `catalogVersion` и `fetchedAt` равны `null`, CMS не
вызывается, отказ каталога не влияет на результат.

### Предупреждения

`warnings` — массив объектов `{ code, message, fields }`. Сейчас единственный
код — `EXTRAPOLATION`: `dtex` выше измеренного диапазона 22.22–3000, но не выше
6000. Расчёт при этом не блокируется. Предупреждения относятся к выданному
результату: в обратном подборе они собираются по совпадениям и схлопываются по
коду. Вне диапазона 22.22–6000 прогноз запрещён валидацией, а не
предупреждением.

## 6. Обратный подбор

`POST /api/rope/v2/reverse`

```json
{ "targetDiameterMm": 1.0, "threadIds": ["tera-40", "tera-60"] }
```

Отклонение считается как `deviation = (D - target) / target`, в ответе —
`deviationPercent = deviation × 100`. В выборку попадает вариант при
`|deviation| ≤ 0.1` — допуск ±10%, граница включительная. Для каждой выбранной
нити проверяются `n` = 1, 2, 3, 4, 5.

Допуск — фильтр близости к целевому диаметру, а не оценка ошибки модели: он не
обещает точность ±10%.

Сортировка результатов, по возрастанию:

1. `|deviation|`
2. `dtex`
3. `threadsPerStrand`
4. `sortOrder`
5. `threadId`

Последние два ключа нужны из-за неизбежных дублей: `mara-15`/`tera-15` (2000),
`mara-30`/`tera-30` (1000) дают одинаковые диаметры. Без дополнительных ключей
порядок зависел бы от порядка входа.

Фильтрация и сортировка выполняются до округления. Смешивание разных нитей в
одной конструкции не поддерживается. Отсутствие совпадений — успешный ответ
`200` с пустым `results` и пустыми `warnings`, а не ошибка.

```json
{
  "apiVersion": "2",
  "algorithmVersion": "4.0.0",
  "modelId": "log-dtex-quadratic-no-load",
  "catalogVersion": "0b24290aff0e",
  "fetchedAt": "2026-11-17T13:00:00.000Z",
  "warnings": [],
  "input": { "targetDiameterMm": 1.0, "tolerance": 0.1, "threadIds": null },
  "results": [
    {
      "threadId": "mara-100",
      "brand": "Mara",
      "number": "100",
      "dtex": 300,
      "threadsPerStrand": 5,
      "construction": "5 × 3",
      "diameterMm": 0.9907175721819338,
      "deviationPercent": -0.9282427818066208
    }
  ]
}
```

## 7. Форматирование в интерфейсе и в тексте MCP

API отдаёт полную точность; округление — обязанность клиента:

- диаметр — три знака после запятой (`1.020`);
- отклонение — два знака в процентах со знаком (`+1.99%`, `-0.93%`);
- если `|deviationPercent| < 0.005`, выводится `0.00%` без знака — правило
  взято из эталонного файла, чтобы не появлялось `-0.00%`;
- единицы — `mm`, конструкция — `N × 3`;
- `brand` и `number` выводятся как строки из CMS без разбора в числа.

Правила одинаковы в интерфейсе и в текстовом ответе MCP. Полные числа в
ответе MCP лежат в `structuredContent`, а не в тексте.

## 8. Каталог и версия

- В ответ попадают только опубликованные записи с `enabled = true`.
- Порядок: `sortOrder` по возрастанию, затем `threadId` по возрастанию.
- `number` — обозначение нити, а не расчётное число.
- `catalogVersion` — первые 12 hex-символов sha-256 от канонического JSON
  массива записей в порядке выдачи с полями `threadId`, `brand`, `number`,
  `dtex`, `sortOrder`, `enabled`. Добавление, удаление или правка любой записи
  меняет версию.
- `fetchedAt` — момент, когда каталог был прочитан из CMS и положен в кеш.

Логика кеша и формат каталога от версии алгоритма не зависят.

## 9. Ошибки

Единый формат:

```json
{
  "error": { "code": "INVALID_PARAMS", "message": "dtex must be between 22.22 and 6000.", "fields": ["dtex"] },
  "requestId": "8f3c1a7b2e40"
}
```

| Код | HTTP | Когда |
| --- | --- | --- |
| `BAD_JSON` | 400 | тело не разбирается как JSON |
| `NOT_FOUND` | 404 | неизвестный маршрут |
| `METHOD_NOT_ALLOWED` | 405 | неподдерживаемый метод |
| `BODY_TOO_LARGE` | 413 | тело больше 8 КиБ |
| `INVALID_PARAMS` | 422 | тип, диапазон, `n` вне 1–5, устаревшее поле нагрузки, пустой `threadIds`, `targetDiameterMm ≤ 0` |
| `THREAD_NOT_FOUND` | 422 | неизвестный или отключённый `threadId` |
| `CATALOG_UNAVAILABLE` | 503 | CMS недоступна и кеша нет |
| `CATALOG_INVALID` | 503 | каталог пуст, неполон или содержит дубли `threadId` |
| `INTERNAL` | 500 | прочие сбои |

## 10. Кеш каталога

- `caches.default` под фиксированным GET-ключом
  `https://rope-catalog.internal/v1?schema=1`; ключ не зависит ни от параметров
  расчёта, ни от версии алгоритма.
- TTL — 86400 секунд через `Cache-Control: public, max-age=86400`.
- Кеш локален для дата-центра Cloudflare и может быть вытеснен раньше TTL.
  Требование — снизить частоту чтения CMS, а не гарантировать одно обращение
  в сутки.
- Ошибки, GraphQL-ошибки и неполный каталог в кеш не пишутся.
- Одновременные промахи схлопываются через `inFlight` Promise в пределах
  изолята; глобальной блокировки нет.
- KV, D1 и Durable Objects не используются.

## 11. Транспорт

- CORS: `https://www.glushkov-modelling.com`, `https://glushkov-modelling.com`,
  `http://localhost:4321`. Методы `GET`, `POST`, `OPTIONS`. Заголовок
  `content-type`. `Vary: Origin`. Preflight — `204`. Credentials не
  используются.
- Лимиты: тело ≤ 8 КиБ, таймаут CMS 5 с, общий таймаут запроса 10 с.
- `requestId` — из `cf-ray`, если заголовок есть, иначе случайный.
- Секрет CMS (`X-GraphQL-Secret`) хранится только в Worker Secrets. Endpoint
  CMS и GraphQL-запрос фиксированы в коде; клиент не может их подменить.
- Код `429` не используется: без хранилища общий лимит частоты нереализуем,
  защита от всплесков — правило Cloudflare на зоне.

## 12. Дефолты интерфейса

Режим — прямой расчёт; основание — каталог; нить — `tera-40`; нитей в пряди —
2; целевой диаметр — `1.00`; в обратном подборе отмечены все нити, а каталог
изначально свёрнут. Интерфейс использует только контракт v2.

## 13. Замороженный контракт v1

`/api/rope/v1/*` сохранён для совместимости: пути, поля, числа и допуск ±10%
не меняются. Отличия от v2:

- формула v1 (`algorithmVersion 2.0.0`), а не модель 4.0.0;
- ручной `dtex` 80–6000 (нижняя граница историческая, не 22.22);
- нет `modelId` и `warnings`;
- ответы без `modelId` и без предупреждений.

Новые возможности в v1 не добавляются. UI и MCP работают только с v2.
Снимок ответов v1 до перехода на v2 сохранён в
`docs/rope-calculator/fixtures/legacy-v1-snapshot.json`.

## 14. Breaking change и миграция

Контракт v2 с грузом (algorithmVersion 3.0.0) был опубликован. Переход на
модель без груза:

1. `apiVersion` остаётся `2`: пути `/api/rope/v2/*` и базовые поля
   (`catalogVersion`, `fetchedAt`, `result`, `results`, `input`) не менялись.
2. `algorithmVersion` повышается `3.0.0` → `4.0.0`, добавляется `modelId`;
   клиент может отличать числа по версии.
3. Из запросов и ответов удалены `loadMode`, `loadGrams`,
   `loadRecommendationVersion`, `totalDtex`, `recommendedLoadGrams`,
   `appliedLoadGrams`, колонка Load. Запрос с этими полями получает
   `422 INVALID_PARAMS`.
4. Миграция клиента: убрать поля нагрузки из запросов; если клиент показывал
   груз, показывать `algorithmVersion`/`modelId` и предупреждения `warnings`.
5. Откат: вернуть предыдущий Worker (algorithmVersion 3.0.0) — пути v2 те же,
   load-поля снова принимаются; UI/MCP при этом должны быть откачены вместе с
   Worker, потому что они больше не отправляют и не показывают груз.

Диаметры меняются вместе с версией алгоритма. Это ожидаемое следствие новой
калибровки, а не регресс: сравнение с предыдущими версиями — в
`docs/rope-calculator/model.md`.

## 15. Вне области

- Пользовательская авторизация и OAuth для калькулятора.
- Серверный rate limiting (код 429).
- Стабильный URL бандла для сторонних страниц (`/widgets/.../v1.js`).
- Кеширование устаревшего каталога дольше TTL.
- Материал-зависимые коэффициенты и выбор нагрузки.

## 16. Встраивание

Скрипт подключён глобально в `src/layouts/BaseLayout.astro` и загружает
компонент только на страницах, где есть элемент, поэтому в статье достаточно
одного тега:

```html
<gm-rope-calculator>
  <noscript>Enable JavaScript to use the rope calculator.</noscript>
</gm-rope-calculator>
```

- `api-base` необязателен: по умолчанию `https://api.glushkov-modelling.com`.
  Внешним страницам его нужно передавать явно; адрес API не выводится из
  `location.origin`.
- `noscript` лежит в light DOM намеренно: без JavaScript элемент не
  апгрейдится и shadow DOM не создаётся, поэтому фолбэк обязан быть обычным
  потомком элемента, а не частью его разметки.
- Порядок загрузки: лоадер (~1 КБ gzip) на всех страницах, сам компонент
  (~5 КБ gzip) — отдельным чанком и только при наличии элемента.
- Внутри компонента нет ни формулы, ни каталога: только запросы к API.
  Проверяется поиском коэффициента формулы в собранном чанке.
- Временная проверочная страница `/rope-preview` закрыта `noindex` и исключена
  из sitemap.
